## Шаг 2.5 — RAG на полных книгах + анти-цитатный guard (вместо дообучения на сыром тексте)

Владелец попросил: модель должна использовать **весь** текст депонированных книг, но никогда не цитировать их клиенту напрямую. Дообучение весов (LoRA/continued pretraining) на сырых главах для этого **не подходит** — на небольшом корпусе это повышает риск дословного запоминания, а не снижает его. Правильная схема — retrieval, не fine-tuning на raw-тексте, плюс обязательная механическая проверка на выходе.

**Задачи:**
1. Индексировать `private/sales-corpus/.extracted/` (полный извлечённый текст, уже есть локально) как базу для поиска по эмбеддингам — по книге, с привязкой к `catalog_id` и `chunk`, как в `rulebook.py`.
2. На ходе генерации движок подтягивает 1–3 релевантных фрагмента как контекст для модели (RAG), с явной инструкцией в промпте: сформулировать мысль своими словами для конкретной ситуации клиента, не пересказывать и не цитировать подтянутый фрагмент.
3. **Анти-цитатный guard** — расширение `src/companion_corpus/mouth_guard.py`: перед отправкой ответа клиенту проверять перекрытие сгенерированного текста с любым фрагментом в `.extracted/` (шинглинг, порог — например 8+ подряд идущих совпадающих слов). При превышении — не отправлять, перегенерировать с явной инструкцией перефразировать иначе; если повторная попытка не проходит — `HANDOFF_TO_HUMAN`, не отправлять как есть.
4. Тесты: подать guard заведомо дословную цитату из депонированной книги → должен блокировать. Подать переформулированную мысль на той же идее → должен пропускать. Оба кейса — в `tests/test_companion_lora_eval.py` или отдельный файл теста guard.

**Готово когда:** RAG подключён как источник контекста (не как обучающие данные весов), анти-цитатный guard ловит дословное совпадение в тестах и встроен в тот же путь, что и остальные проверки `mouth_guard`.

## Шаг 5 — shadow-прогон перед живым включением

Прежде чем трогать `AI_PROVIDER`, нужно увидеть модель на реальных (или close-to-real) диалогах без риска для живого лида.

**Задачи:**
1. Поднять `scripts/serve_companion_mouth.py --run` с лучшей версией адаптера в режиме shadow: модель получает те же входы, что реальный прод-провайдер, её ответ **логируется**, но не отправляется лиду.
2. Сравнить её ответы с ответами прод-провайдера на одних и тех же реальных ходах (N диалогов, согласовать с владельцем объём) — разметить расхождения: где companion формулирует лучше/хуже/опаснее (проверка через тот же `mouth_guard` — сколько раз guard сработал не на ожидаемый STOP/injection кейс, а на реальную продажную реплику — это сигнал, что модель нестабильна).
3. Отчёт: частота срабатывания guard на «нормальных» ходах, частота совпадения по смыслу с прод-ответом, субъективная оценка тона.

**Готово когда:** есть отчёт по shadow-прогону с конкретными цифрами расхождений, не просто «вроде работает».

## Шаг 6 — решение о включении (только с владельцем)

Агент не переключает `AI_PROVIDER` самостоятельно. Решение принимается только после:
- шаг 1–2 закрыли известные дыры покрытия;
- шаг 2.5 — анти-цитатный guard подключён и проходит тесты на дословное совпадение;
- шаг 3 дал версию не хуже v3 по val loss и лучше по per-move eval;
- шаг 4 — карточки утверждены владельцем;
- шаг 5 — shadow-прогон без тревожных сигналов guard на нормальных ходах **и** без единого случая дословного совпадения с корпусом в логах shadow-прогона.

Если всё это выполнено и владелец явно просит — включение делается как отдельный, обратимый шаг (флаг, не удаление прежнего провайдера), с планом мгновенного отката.
