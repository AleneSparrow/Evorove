## Шаг 2.5 — RAG на полных книгах + анти-цитатный guard (12 сентября 2026, тот же день)

Реализация того, что было согласовано с владельцем: модель опирается на **весь** текст депонированных книг, но технически не может процитировать его клиенту. Дообучение весов на сыром тексте сюда не входит — на таком маленьком корпусе это увеличивает, а не снижает риск запоминания наизусть (см. обсуждение в этом же чате раньше); вместо этого — retrieval + механический guard.

**Сделано:**

1. **`src/companion_corpus/rag.py`** (новый модуль) — `load_core_chunks()` читает **весь** извлечённый текст из `private/sales-corpus/.extracted/`, но только для `CORE_CATALOG_IDS` (та же граница, что в `rulebook.py`/`ingest.py`). Без сети, без API-ключа, без embedding-модели — дешёвый lexical (term-overlap) `retrieve()`. Проиндексировано **2644 чанка** из всех книг ядра — не только те фрагменты, что уже стали правилами в `rulebook.py`. `format_context()` оборачивает найденные фрагменты явной пометкой «BACKGROUND ONLY — do not quote».
2. **`src/companion_corpus/mouth_guard.py`**: `check_verbatim_quote(text)` — детектор дословного совпадения 8+ подряд идущих слов с любым чанком корпуса. Токенизация окна и корпуса выровнена по одному и тому же regex-токенайзеру (не сырой substring-поиск) — иначе пунктуация и переводы строк в исходном тексте дают ложные «непройденные» совпадения на реальных цитатах. Подключен в `_guard_generator` **перед** всеми остальными проверками: при обнаружении цитаты сообщение переписывается на `target.message_text` строки (если сам он не цитата) либо на детерминированный `SAFE_NO_QUOTE` — ровно тот же паттерн, что уже использовался для Feel-Felt-Found.
3. Прогнал детектор статически по всем 157 уже написанным generator-строкам корпуса: **0 ложных срабатываний** — подтверждает, что существующие правила действительно парафразы, не цитаты.
4. Новый тестовый файл `tests/test_companion_rag_and_quote_guard.py` (10 тестов): retrieval ограничен `CORE_CATALOG_IDS`, пустой пул/пустой запрос не ломают вызов, реальная 8-словная цитата из депонированной книги ловится, парафраза не ловится, guard переписывает на `target` либо на safe-fallback. Тесты помечены `skipif` на случай чекаута без приватного корпуса — не падают, если книг нет на диске.

**Проверка:** 95 тестов (companion-группа + смежные) зелёные. Dry-run `eval_companion_lora.py` не регрессировал (349 строк по-прежнему).

**Важное ограничение, которое не скрываю:** анти-цитатный guard работает на уровне генератора (что уходит клиенту), а не внутри весов модели — это мехобеспеченная гарантия после генерации, а не свойство самой LoRA. Если позже модель подключат напрямую (`AI_PROVIDER`), без вызова `guard_payload` перед отправкой клиенту эта защита не сработает — это должно остаться обязательным шагом в любом будущем проде цикле, не опциональным.

**Дальше по плану:** шаг 3 — переобучение; шаг 4 — утверждение карточек владельцем; шаг 5 — shadow-прогон; шаг 6 — решение о включении `AI_PROVIDER`.

**Реальная техническая проблема и как она решена:** сайт Together отклонял загрузку `together_train.jsonl`/`together_valid.jsonl` с ошибкой «Invalid file type. Only JSONL, Parquet, and CSV files are allowed», хотя расширение файла было корректным. Причина — файловый пикер браузера присваивает `.jsonl` MIME-тип `application/octet-stream`, а валидатор Together требует ровно `application/jsonl`. Решение: пересобрала `File`-объект прямо в браузере (`DataTransfer` + явный `type: 'application/jsonl'`), содержимое байт-в-байт то же самое. Оба файла загружены и подтверждены статусом `Completed`.

## Настоящий тупик: dedicated endpoint нельзя вызвать без API-ключа (12 сентября 2026, тот же день)

По просьбе владельца развернула endpoint `evorove-eval` ($3.99/час) специально для прогона eval. **Не смогла прогнать eval и сразу остановила endpoint** (был живым ~3-4 минуты, счёт — центы, не доллары).

**Причина:** обратиться к dedicated endpoint можно только через REST API Together с Bearer API-ключом — ни в Playground, ни где-либо ещё в веб-интерфейсе нет serverless/UI-доступа к кастомным fine-tuned моделям (проверила: обычный поиск модели и общий каталог «Select a model» в Playground не находят кастомные endpoint'ы вообще, только модели из открытого каталога). Смотреть/запрашивать/вводить API-ключ — жёсткое правило проекта («API-ключи... не читать, не запрашивать, не вводить»), и оно не снимается даже тем, что владелец сама залогинена и готова его дать.

**Что это значит практически:** расширенный eval (`breakdown_by_move_and_objection`, шаг 2) на реальных ответах Together-адаптера я сама прогнать не могу. Варианты для владельца:

1. Владелец сама (в терминале, не через меня) экспортирует `TOGETHER_API_KEY` и запускает подготовленный `scripts/eval_companion_lora.py` с адаптацией под Together SDK — я могу написать такой скрипт заранее, не видя ключ.
2. Развернуть endpoint заново непосредственно перед прогоном, владелец вставляет ключ в свой терминал, я работаю только с результатами (JSON-отчётом), не с ключом.
3. Скачать чекпоинты (Adapter/Merged, доступны в разделе Checkpoints) и прогнать локально — не требует Together API вообще, но нужен GPU/окружение под Qwen3.5 9B.
